# 0001. Generated profile README built by TypeScript and refreshed by GitHub Actions

**Date**: 2026-11-16
**Status**: In Progress

## Summary

Your profile lives in the public repo `nguyen-duc-loc/nguyen-duc-loc`, and you never edit its `README.md` by hand. A small TypeScript program running on Node.js 26 builds the README and its images from your content data and from saved copies of outside data (LeetCode, Credly, GitHub). One GitHub Actions workflow rebuilds and commits the result once a day, when you click "Run workflow", and whenever you push a change to the data or the code. If an outside service fails, the last good copy stays on the page and the run turns red so you hear about it.

## Requirements

**User stories**:
- As a visitor to github.com/nguyen-duc-loc, I want to see a working profile README so that I learn who Loc is.
- As Loc, I want to change my profile by editing a data file and pushing, so that I never touch README layout by hand.
- As Loc, I want outside stats to refresh on their own, and to get an email on every run where a source failed, so that the page stays current without showing broken cards.

**Acceptance criteria**:
- **AC-1**: The public repo `nguyen-duc-loc/nguyen-duc-loc` exists, and github.com/nguyen-duc-loc shows a README with the name "Loc Nguyen", the title "Cloud Developer", and a short "profile under construction" note, exactly as in *Placeholder output* below. The first commit already contains a locally built `README.md`, so the profile renders before any workflow runs.
- **AC-2**: On a fresh clone, `pnpm install` then `pnpm build` regenerates `README.md` (and anything under `assets/generated/`) with no network access, and `git status` is clean right after that first build and after a second one (the output is deterministic, meaning the same input always gives byte for byte the same output).
- **AC-3**: Changing `title` in the starter data and pushing only that change (no locally rebuilt `README.md`) to `main` updates the profile within one workflow run, with no hand edit of `README.md`. The commit that updates `README.md` is authored by `github-actions[bot]`.
- **AC-4**: The workflow runs daily at 02:17 `Asia/Ho_Chi_Minh` and on manual "Run workflow". A run where nothing changed creates no commit.
- **AC-5**: `pnpm refresh` fetches each registered outside source on its own. A source that fails (network error, timeout, error status, or a response that fails validation) keeps its previous snapshot file unchanged, the sources that worked are still written and committed, and the workflow run ends failed and names the failed sources. (The framework ships now with zero sources; features 8, 10, and 12 register the first ones and are where this is first verified end to end.)
- **AC-6**: When a run on `main` has nothing to commit and the latest commit on `main` is older than 45 days, the run commits an updated `.github/last-refresh` file. Locally, `node src/keepalive.ts --days 0` rewrites that file (and commits nothing).
- **AC-7**: Every `uses:` in the workflow is pinned to a full 40 character commit SHA with a `# vX.Y.Z` comment. The workflow sets `permissions: {}` at the top, grants only `contents: write` to the `profile` job, and only `contents: read` to the `readme` job. `.github/dependabot.yml` opens weekly grouped update PRs for `github-actions` and `npm` (which covers pnpm), as in *Dependabot config* below.
- **AC-8**: `pnpm build` fails with a clear message, and writes no files, if the README text contains an `<img>` with a missing or blank `alt`, or any Markdown image (`![...](...)`). This enforces the scope rule that every image has alt text from day one.
- **AC-9**: Every pull request to `main` (including Dependabot PRs) runs `pnpm typecheck`, `biome ci`, and `pnpm build`, and the check fails if the build changes any committed file. PR runs never commit or push.
- **AC-10**: Every push to `main` and every pull request runs markdownlint and lychee on the built `README.md` in a job with only `contents: read`. A lint problem or a dead link fails the run, but never stops the bot's commit.

## Decision

**Chosen option**: Option 1: Generated README, TypeScript on Node.js 26, snapshots committed, one GitHub Actions workflow.

The README is fully generated by typed section functions from your content data and committed source snapshots. GitHub Actions runs `refresh` (fetch, then build) on a schedule and `build` on push, and commits only real changes straight to `main`.

**Implementation skills**: `node` (`mcollina/skills`, `.kiro/skills/node/`) · `octocat` (`mcollina/skills`, `.kiro/skills/octocat/`) · `github-actions-hardening` (`github/awesome-copilot`, `.kiro/skills/github-actions-hardening/`) · `dependabot` (`github/awesome-copilot`, `.kiro/skills/dependabot/`)

### Commands

| Command | Does | Network |
|---|---|---|
| `pnpm build` | `node src/build.ts`. Reads `content/` and `data/snapshots/`, runs the guards on the rendered README text, then writes `README.md` and `assets/generated/` | None |
| `pnpm refresh` | `node src/refresh.ts`. Runs every registered fetcher, writes the snapshots that succeeded, then runs build | Yes |
| `pnpm typecheck` | `tsc --noEmit` | None |
| `pnpm lint` | `biome check` (CI runs `biome ci`) | None |
| `pnpm lint:md` | `markdownlint-cli2` on `README.md` | None |

### tsconfig essentials

`strict`, `noEmit`, `module: nodenext`, `moduleResolution: nodenext`, `target: esnext`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `types: ["node"]` (newer TypeScript no longer loads all `@types` by default), `include: ["src", "content"]`. Imports use the `.ts` extension, and type imports use `import type`. No enums, namespaces, parameter properties, or decorators (Node's type stripping rejects them; use `as const` objects instead).

### Build behavior

- **Order.** `build` loads content and snapshots, renders the README text in memory, runs the guards on that text, and only then clears `assets/generated/` (keeping `.gitkeep`) and writes `README.md` plus the SVGs. A failed guard writes nothing.
- **Alt text guard (`src/guards.ts`).** It checks the README text only, not the inside of SVGs. Every `<img ...>` tag (matched case insensitively) must have a non blank `alt`. Markdown image syntax `![...](...)` is rejected outright, since light and dark images need `<picture>` HTML anyway.
- **Missing snapshot.** If a registered source has no snapshot file, `build` fails with `missing snapshot <source>: run pnpm refresh locally and commit data/snapshots/<source>.json`. Each source feature commits its first snapshot together with its code.
- **Serialization.** Snapshots are JSON with keys sorted at every level, 2 space indent, LF line endings, and exactly one trailing newline. Each source declares a stable sort key for its arrays (for example badge id), so a change in API order alone never produces a commit. `README.md` and SVGs use LF line endings and end with exactly one newline.

### Source fetcher contract (for features 8, 10, 12)

Each `src/sources/<name>.ts` exports `{ name, sortKey, fetch(signal: AbortSignal): Promise<unknown>, validate(raw): Snapshot }`. `refresh.ts` runs them all with `Promise.allSettled` and passes each call `AbortSignal.timeout(15000)` (a 15 second timeout).
- **Retry.** One retry after 2 seconds, only for a network error, a timeout, a 5xx status, or a 429 (too many requests). A 4xx status or a failed `validate` is never retried.
- **Writing.** A successful source overwrites its snapshot atomically (write a temp file, then rename it). A failed one leaves the file untouched.
- **Reporting.** When the environment variable `GITHUB_OUTPUT` is set (that is, inside Actions), `refresh.ts` always appends a `failed_sources=<comma list>` line, which is empty when everything worked. For each failure it also appends a Markdown list item (source name plus status code, `timeout`, or `validation failed`) to `GITHUB_STEP_SUMMARY`. Locally it prints the same list as a warning.
- **Exit code.** 0 after a partial failure, because the outputs are valid. Non zero only on a hard error (a crash, or a failed build or guard).

### Keepalive script

`node src/keepalive.ts --days <n>` reads the latest commit time with `git log -1 --format=%ct`. If that is older than `<n>` days, it writes today's UTC date (`YYYY-MM-DD`) plus a newline to `.github/last-refresh`. It never stages, commits, or pushes; the workflow does that. It exits 0 whether or not it wrote, and fails with a clear message outside a git repo.

### Workflow design (`.github/workflows/profile.yml`)

| Concern | Decision |
|---|---|
| Triggers | `schedule: cron "17 2 * * *"` with `timezone: Asia/Ho_Chi_Minh` (add a comment that `17 19 * * *` in UTC is the same time, since Vietnam has no daylight saving) · `workflow_dispatch` · `push` to `main` with `paths: content/**, src/**, data/snapshots/**, assets/static/**, package.json, pnpm-lock.yaml, tsconfig.json, pnpm-workspace.yaml, biome.json, .markdownlint-cli2.jsonc, lychee.toml, .node-version, .github/workflows/profile.yml` · `pull_request` to `main` |
| Permissions | Top level `permissions: {}`. The `profile` job gets `contents: write` only. The `readme` job gets `contents: read` only. On pull requests from Dependabot or forks, GitHub makes the token read only anyway |
| Concurrency | `group: profile-${{ github.ref }}`, `cancel-in-progress: false`, so each branch and each PR has its own group. A running workflow run always finishes. GitHub lets only one run wait per group, and a newer waiting run cancels the older one. That is harmless inside one group: on `main` the newest waiting run carries the newest commit (each run checks out the commit that triggered it), and on a PR it carries the newest push to that PR. Groups never cancel each other, so a PR check can never be cancelled by a run on `main` or on another PR. Do not go back to one shared group: verify on 2026-11-16 showed it cancelled a PR check before it started, leaving the PR with no check at all |
| Setup | `actions/checkout` (v7) with `persist-credentials: false`, then `pnpm/action-setup` (v6) with no `version:` input (it reads `packageManager`), then `actions/setup-node` (v7) with `node-version-file: .node-version` and `cache: pnpm`, then `pnpm install --frozen-lockfile`. In the `profile` job, the install step sets `SKIP_INSTALL_SIMPLE_GIT_HOOKS: "1"` in `env:`, so the bot's commits never run the local pre-commit hook |
| Steps, in order (`profile` job) | 1. `pnpm typecheck` (always). 2. `pnpm exec biome ci` (always). 3. `pnpm build`, if `github.event_name` is `push` or `pull_request`. 4. `pnpm refresh` with `id: refresh`, if the event is `schedule` or `workflow_dispatch`. 5. On `pull_request` only: `git diff --exit-code`, then a `git status --porcelain --untracked-files=all` check (fails if the build changed a committed file or left a new one). Steps 6 and 7 are skipped on pull requests by their own `if:`. 6. Commit step, `id: commit` (below). 7. Keepalive, only if `steps.commit.outputs.committed == 'false'`. 8. Fail step (below). A hard failure in steps 1 to 4 stops the job, so nothing is committed |
| Main only | Steps 6 and 7 run only when `github.ref == 'refs/heads/main'` and the event is not `pull_request`. A manual run on another branch builds and refreshes but never pushes |
| Git identity | `git config user.name "github-actions[bot]"` and `git config user.email "41898282+github-actions[bot]@users.noreply.github.com"` |
| Commit | `git add README.md assets/generated data/snapshots .github/last-refresh` (`git add -A` on those paths, so deleted SVGs are staged too). If `git diff --cached --quiet` reports changes, commit with `chore(refresh): update generated profile`, push, and set `committed=true`. Otherwise set `committed=false` |
| Push | With `GH_TOKEN: ${{ github.token }}` in `env:`, run `git push "https://x-access-token:${GH_TOKEN}@github.com/${GITHUB_REPOSITORY}.git" HEAD:refs/heads/main` |
| Keepalive | `node src/keepalive.ts --days 45`. If `.github/last-refresh` changed, stage it, commit with `chore(keepalive): record refresh`, and push the same way |
| Fail step | Runs with `if: always() && steps.refresh.outputs.failed_sources != ''`. It receives the list through `env: FAILED: ${{ steps.refresh.outputs.failed_sources }}` and runs `echo "Failed sources: $FAILED"; exit 1`. GitHub then emails you about the failed run |
| Push race | If you push while a run is in progress, that run's push is rejected and the run fails. The run triggered by your push then rebuilds from your new commit. No force push, and no automatic rebase of generated files |
| Timeout | `timeout-minutes: 10` on each job |
| Untrusted input | No `${{ }}` interpolation inside `run:` scripts at all. Every value goes in through `env:` |
| `readme` job | A second job in the same workflow, with `if: github.event_name == 'push' \|\| github.event_name == 'pull_request'` (never the schedule or a manual run), `contents: read`, and `timeout-minutes: 10`. Same setup as above (the hook skip is not needed, since it never commits). Steps: `pnpm build`, then `pnpm lint:md`, then `lycheeverse/lychee-action` (SHA pinned) with `args: --no-progress README.md` and `failIfEmpty: false` (the placeholder has no links yet). It runs beside the `profile` job and never blocks its commit |

Bot pushes made with `GITHUB_TOKEN` do not trigger workflows, so refresh commits never cause a loop.

### Dependabot config (`.github/dependabot.yml`)

Two entries, `github-actions` and `npm`, both with `directory: "/"`, `schedule.interval: weekly` on `monday`, one group per ecosystem with `patterns: ["*"]`, and `commit-message.prefix: chore(deps)`. The `npm` entry ignores `semver-major` updates of `@types/node`, so the types stay on Node 26. `@biomejs/biome` gets its own `biome` group, listed before the catch all `npm` group, so a Biome bump that changes formatting and fails `biome ci` never blocks the other npm updates. When you merge a Biome bump, run `pnpm exec biome migrate --write` in the PR so the `$schema` version in `biome.json` matches. Merging a Dependabot PR triggers the `push` run, which rebuilds if needed.

### Key invariants

- `README.md` and `assets/generated/` are only ever written by `pnpm build`.
- Build output is deterministic: no timestamps, random IDs, or unsorted object keys in `README.md`, SVGs, or snapshots. Snapshots store fetched data only, never a "fetched at" time (git history already records when a snapshot changed). This keeps "commit only when changed" honest.
- `build` never touches the network. Only `refresh` does.
- A snapshot file is replaced only by a successful, validated fetch.
- The workflow never force pushes and never commits outside the paths listed in the Commit row.

### Security model

The repo is public, and all content in it is public. There are no stored secrets. The `profile` job's `GITHUB_TOKEN` can write repo contents and nothing else. The `readme` job's token is read only, so the third party link checker (which receives the token by default) never holds write access. Outside sources are read through their public endpoints. If a later source needs a token, that feature's spec adds it as a repo secret and names it here under Configuration. All actions are SHA pinned, and Dependabot proposes the updates as PRs you review.

### Configuration required

- None now. Under Settings, Actions, General, keep the default workflow permissions at "Read repository contents" (the workflow raises only its `profile` job to `contents: write`).
- Leave `main` without branch protection or rulesets. If either is added later, the bot's pushes with `GITHUB_TOKEN` are rejected.

### Delivery shape (Skateboard)

The first shippable slice is the whole pipeline with one section. That means the bootstrap push, the starter data, `pnpm build` rendering the placeholder, the workflow with all four triggers (including the pull request check), the commit step, the keepalive, the alt text guard, Dependabot, and an empty source registry. It goes live on your profile before any real section is built. Features 5 to 14 then each add a section function (and, where needed, a source) on top of it, keeping the profile live at every step.

## Consequences

**Positive**:
- Editing `content/profile.ts` and pushing is the only way to change the profile, so the layout and data stay separate.
- An outside outage never breaks the page. It shows the last good data and sends you a red run email on every day a source fails (no threshold, by choice).
- `pnpm build` is fast, offline, and safe to run as often as you like.
- No servers, no secrets, and no cost.

**Negative / tradeoffs**:
- `main` history gains up to one bot commit a day when data changes. Filter it with `git log --invert-grep --grep='^chore(refresh)'`.
- On `main`, a push run can replace a scheduled or manual run that is waiting behind another run. Push runs build but do not refresh, so that day's outside data is skipped and the next scheduled run picks it up. This needs three runs on `main` to overlap, which is rare for one person's repo, so it is accepted.
- Committed SVGs and snapshots make the repo grow slowly over time. This is small for text SVGs, but heavy animated GIFs (feature 13) would add up faster.
- Node's type stripping rules out enums, namespaces, and decorators, so code follows that subset.
- The daily schedule can run late at busy times. GitHub may delay scheduled runs and can drop some under heavy load.
- The 60 day rule is only partly covered. GitHub's docs don't say whether commits made by the workflow count as "repository activity". If they don't, the keepalive commit won't prevent the disable either (see Follow-up).
- A rejected push during a race fails one run, which emails you. That is noise, though harmless.

**Neutral**:
- `content/profile.ts` is a starter. Feature 3 decides the real data shape and format, and may replace this file. Only `src/build.ts` and the section functions read it.
- The look (colors, fonts, SVG card style, animation) belongs to feature 4. This spec only fixes where images live and how they are linked.
